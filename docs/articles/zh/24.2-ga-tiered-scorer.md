# TieredScorer：三层评分流水线与 LLM 预算管理

> 本文深入 `internal/ares_evolution/scoring/` 的三层评分流水线：`TieredScorer`（Cache → LLM → Heuristic）、`Budget`（CAS 原子预算）、`ScoreCache`（LRU + 代际过期），以及可选的 `MemoryAwareScorer` 叠加层。代码片段都来自真实源码；常量与默认值均与仓库一致。

---

## 1. 架构概览

`TieredScorer` 决定一条策略的适应度分数。它的核心思想是**用最便宜的层级给出足够好的评分，仅在必要时才调用昂贵的 LLM**。文件路径 `internal/ares_evolution/scoring/tiered_scorer.go`。

```mermaid
flowchart LR
    S[Score(strategy)] --> H1[StrategyHash]
    H1 --> C{1. cache 命中?}
    C -->|命中| R1[返回缓存值 + CacheHit]
    C -->|未命中| B{2. llm 存在且 budget 允许?}
    B -->|是| L[tryLLMScore 带 panic recovery]
    L -->|成功| R2[返回 LLM 分 + 写缓存]
    L -->|失败| H[3. heuristic 兜底]
    B -->|否| H
    H --> R3[heuristic 分 + 写缓存]
```

## 2. Tier 定义与执行顺序

### 2.1 枚举

```go
const (
    TierCache     Tier = iota + 1  // 1
    TierHeuristic                   // 2
    TierLLM                         // 3
)
```

注意一个**真实的命名/执行顺序不一致**：枚举的数值顺序是 Cache(1) → Heuristic(2) → LLM(3)，但在 `Score()` 的**实际执行顺序**里，LLM 排在 Heuristic **前面**：

```go
func (ts *TieredScorer) Score(ctx context.Context, s *mutation.Strategy) (float64, Tier, error) {
    hash, err := StrategyHash(s)          // FNV-1a 64 位哈希
    if err != nil { ... }

    // Tier 1：缓存命中直接返回（零成本）
    if entry, ok := ts.cache.Get(hash); ok {
        ts.budget.RecordCacheHit()
        ts.cacheHits.Add(1)
        ts.totalScored.Add(1)
        return entry.Score, TierCache, nil
    }

    // Tier 2：LLM 存在且预算允许
    if ts.llm != nil && ts.budget.TryRecordLLMCall() {
        score, scored := ts.tryLLMScore(ctx, s, hash)
        if scored {
            return score, TierLLM, nil
        }
        // LLM 失败/panic → 落入 heuristic
    }

    // Tier 3：heuristic 兜底（始终可用）
    score := ts.heuristic(s)
    entry := MakeEntry(hash, score, ScorerTypeHeuristic, 1, 0.5)
    ts.cache.Put(hash, entry)
    ts.heuristicCalls.Add(1)
    ts.totalScored.Add(1)
    return score, TierHeuristic, nil
}
```

原因：虽然 LLM 贵，但它比启发式**更准**，所以流水线先尝试更准的层级，只有预算见底或 LLM 失败才降级。

### 2.2 LLM panic 安全 recovery

```go
func (ts *TieredScorer) tryLLMScore(ctx context.Context, s *mutation.Strategy, hash uint64) (float64, bool) {
    var score float64
    var success bool
    func() {
        defer func() {
            if r := recover(); r != nil {
                log.Warn("tiered_scorer: LLM scorer panicked", "hash", hash, "recovery", r)
                ts.budget.RecordFallback()
                ts.fallbacks.Add(1)
                success = false
            }
        }()
        score = ts.llm(s)
        success = true
    }()
    if !success {
        return 0, false
    }
    entry := MakeEntry(hash, score, ScorerTypeLLM, 1, 1.0)
    ts.cache.Put(hash, entry)
    ts.llmCalls.Add(1)
    ts.totalScored.Add(1)
    return score, true
}
```

LLM 调用用闭包 + `defer recover()` 包住：即使评分子 panic，进化循环也不崩，而是优雅回落 heuristic。

`Stats()` 返回 `cache_hits` / `llm_calls` / `heuristic_calls` / `fallbacks` / `total_scored`；`ResetForGeneration()` 每代开头重置 budget 与各类计数。

## 3. Budget：CAS 原子预算

`internal/ares_evolution/scoring/budget.go`。控制**每一代**的 LLM 调用上限。

```go
type Budget struct {
    MaxLLMCalls   int64        // 每代最大 LLM 调用（不可变）
    UsedLLMCalls  atomic.Int64 // 当前代已用数量
    CacheHits     atomic.Int64
    FallbackCount atomic.Int64
}
```

核心 CAS 自旋：

```go
func (b *Budget) TryRecordLLMCall() bool {
    used := b.UsedLLMCalls.Load()
    for used < b.MaxLLMCalls {
        if b.UsedLLMCalls.CompareAndSwap(used, used+1) {
            return true
        }
        used = b.UsedLLMCalls.Load()
    }
    return false
}
```

无锁并发：读当前用量 → 若未超限尝试 CAS 递增 → CAS 失败（别的 goroutine 抢先）重试 → 成功返回 true → 已超限返回 false。另有 `CanCallLLM()`、`RecordCacheHit()`（不耗预算）、`RecordFallback()`；`Reset()` 置零计数器。

## 4. ScoreCache：LRU + 代际过期

`internal/ares_evolution/scoring/cache.go`。用 `container/list` 做 LRU，以策略哈希为键。

```go
type CacheEntry struct {
    Hash        uint64  // 策略哈希
    Score       float64
    ScorerType  string  // "llm" / "heuristic"
    Timestamp   int64   // Unix nanos
    SampleCount int
    Confidence  float64
}

type ScoreCache struct {
    mu          sync.RWMutex
    entries     map[uint64]*list.Element
    lru         list.List   // front = 最近使用
    maxSize     int         // 0 = 不限
    maxCacheAge int         // 0 = 不限（无代际过期）
    generation  uint64
    hits, misses, evictions int64
}
```

两个真实的设计点：

- **`Get()` 用的是写锁**：因为它会 `MoveToFront` 改变 LRU 顺序，`sync.RWMutex` 下写锁更简单。
- **代际过期是 opt-in**：`maxCacheAge` 默认 `0`（**不限**，不会自动过期）。要启用就在 `SetMaxCacheAge(n)` 后由 `NewGeneration()` 递增代数；条目存活超过 n 代即按 miss 处理并逐出。旧版文章写"默认 maxCacheAge=2、3 代后失效"——**这是错的**，默认是没有过期限制的。

`Put()` 在容量满时从链表尾部逐出最久未用条目；已存在哈希则原地更新并刷新代数。

## 5. MemoryAwareScorer：经验驱动的叠加层

`internal/ares_evolution/scoring/memory_aware_scorer.go` 在 TieredScorer 之上叠加经验记忆维度。默认配置（均为真实常量）：

```go
func DefaultMemoryAwareScoringConfig() MemoryAwareScoringConfig {
    return MemoryAwareScoringConfig{
        Enabled:               false,  // 默认关闭
        MemoryWeight:          0.2,
        CostWeight:            0.1,
        LatencyWeight:         0.05,
        RegressionWeight:      0.1,
        MinEvidenceBonus:      0.0,
        MaxEvidenceBonus:      20.0,
        ExperienceLookupLimit: 10,
        SuccessRateBonusScale: 10.0,   // bonus = success_rate * confidence * scale
        LatencyPenaltyScale:   1.0,     // penalty = (latency_p50 / 10000) * scale
        ErrorRatePenaltyScale: 1.0,
    }
}
```

它的方向是 `quality + memory_evidence_bonus − cost − latency − regression`，成功奖励与延迟/错误惩罚的公式写在配置字段注释里。`ScoreDetail` 结构体把每一项分量拆开用于报告。

## 7. 小结

三层流水线的"成本—质量权衡"落地在真实代码里：

1. **Cache** 用 O(1) 哈希查询挡掉重复评分，`Get`/`Put` 更新 LRU。
2. **Budget** 用 CAS 自旋在并发下精确控制每代 LLM 调用次数。
3. **heuristic** 永远兜底，任何情况都有分数。
4. **MemoryAwareScorer** 把历史经验作为可开关的叠加层（默认 `Enabled:false`）。

只要是"要花 LLM 的钱才能出分"的地方，这套层叠就是评分侧的第一道、也是最重要的一道成本闸门。
