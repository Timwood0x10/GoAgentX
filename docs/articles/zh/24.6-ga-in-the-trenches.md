## 二、教训 1：接口里不放没人调用的方法

`internal/evolution/genome/genome.go` 的包注释（2026-07 改动）：

> `Crossover` 和 `Fitness` 因为"零生产调用者"从核心 `Genome` 接口里移除，改成可选的 `CrossoverGenome` / `FitnessGenome`。

这就是一个典型的"实战真相"：**接口要长得像真实调用面，而不是像论文里的理想面。** 每个没被调用的方法都在误导实现者——你以为子系统都会交叉、都会打分，其实运行时只有 Mutate/Snapshot 是硬需求。判断是否保留扩展点，应该用 `grep` 数调用者，而不是凭直觉。

配合这条：`internal/ares_evolution/genome/genome.go` 里 `Crossover` 和 `Fitness` 也同样是可选能力。两处口径一致。

## 三、教训 2：一个"退役"的基因组名字还在误导人

`internal/evolution/genome/workflow_genome.go`：

```go
// SchedulerGenomeName is RETIRED (fusion plan §B1, 2026-08-22): the
// scheduler dimension no longer participates in genome mutation/diff.
// Kept only as a historical identifier for legacy persisted patches.
SchedulerGenomeName = "scheduler"
```

scheduler 维度已经退出 GA mutation/diff，但常量**保留**，因为它可能出现在历史持久化补丁里。删除一个"看起来没用"的标识符，会让旧数据在反序列化/查询时失配。工程教训：**改名/退役前，先确认有没有历史数据引用它；要留，就在注释里写明为什么留。**

## 四、教训 3：元数据在替换节点时差点悄悄丢了（C4）

`workflow_genome.go` 的 `mutateReplaceNode` 有一段很关键的注释和代码（C4 作动面）：

```go
// C4: preserve Metadata through replace – previously the new step was
// built without Metadata, which meant a metadata-only gene mutation
// produced ZERO patches ... evolution could never select for a metadata variant.
```

之前 `ReplaceNode` 构造新 step 时**忘了拷贝 `Metadata`**，后果是：`mutateSetMetadata` 这种只改元数据的变异，产出的 child 在 diff 引擎眼里和父代**拓扑完全一样** → 差分结果是 0 个补丁 → 进化永远选不中元数据变体。修复就是复制一份 `mdCopy` 再塞回 `Metadata`。

> 这是个教科书级的"初始化坑"：不是架构决策错了，是一行字段没传。旧版 24.6 讲的"Wired 模式是瓶颈"其实是同一类错误的更大号版本——只是这次我能把根因钉死在真实代码上。

## 五、教训 3b：配套的 mutateSetMetadata 算子

同一文件里的 `mutateSetMetadata()` 专门为了让元数据变异成为可能而存在——它把随机节点的 `budget` 属性在 `"" → "10" → "20 → "10"` 之间翻转：

```go
const budgetKey = "budget"
switch md[budgetKey] {
case "":    md[budgetKey] = "10"
case "10":  md[budgetKey] = "20"
default:    md[budgetKey] = "10"
}
g.dag.SetNodeMetadata(step.ID, md)
```

注释点明动机：*"Without this operator, evolution could never explore the metadata dimension."* 教训：**你想让一个维度可进化，光改 diff 还不够，还要给基因组一个能产生"只在该维度不同"的子代的变异算子**——否则那条探索路径永远是空的。

## 六、教训 4：注册用 Replace 而非 Register（#25）

`candidate_pipeline.go` 里，同一个 TargetRole 被二次放行时：

```go
// Replace, not Register (#25): the registry has no unregister path, so a
// second verified candidate for the same TargetRole must be able to
// supersede the first — Register would fail with "already registered".
if err := p.registry.Replace(target, p.executor); err != nil { ... }
```

工程教训很朴素：**当底层接口没有 unregister 时，"幂等地覆盖"必须用 Replace 而不是会失败的 Register**，否则第二个同类候选永远按同一个 bug 失败。这属于"看了 registry 的实现才知道要怎么写"的集成细节。

## 七、教训 5：协调器的软默认值会互相掩盖（a952206e）

`internal/evolution/coordinator/coordinator.go` 的 `DefaultPolicy()` 注释讲了一个真实修复：

> 之前设置 `AutoApplyThreshold` 后有一处 `fallthrough`，导致**所有** patch 都走 apply、`AutoApplyThreshold` 形同虚设。改成显式逻辑后，才真正让：`Priority>=8` 自动应用、GA fitness `>=70` 自动应用、`<30` 拒绝、`[30,70)` 进 delay 待人工。

真实常量：

```go
AutoApplyThreshold:    8,
MaxPatchesPerMinute:   4,
MinFitnessThreshold:   30.0,
ApplyFitnessThreshold: 70.0,
```

教训：**一个 `fallthrough` 就能让一个"安全阀"失去意义。** 配置项写得再多，也要有测试证明它们真的被走到的分支用了——代码注释坦诚记录了这个坑。

## 八、教训 6：补丁没人执行时——DAGPatchExecutor 兜底

`internal/workflow/engine/dag_patcher.go` 里 `DAGPatchExecutor` 的注释说明它是 **patch registry 的 fallback**：之前一个 workflow 补丁会因为"没有给目标节点注册 executor"而直接死，现在 fallback 会直接改**活的 `*MutableDAG`**（`runtime.GetAgentDAG` 拿到的同一个对象），形成跨图闭环（Step 7.1）。

```go
// It is wired as the patch registry's fallback so a workflow patch no longer
// dies on "no executor registered for target <nodeID>"; instead it mutates the
// real live DAG. This is the closure the cross-graph fix unlocks.
```

`Snapshot`/`Restore` 实现 `patch.Restorable`，部署回滚能在原位把 DAG 还原（`*MutableDAG` 指针不变，运行管理器、`WorkflowGenome` 和其他 executor 都看到还原后的图）。

## 九、把这些串起来：真正的"GA in the trenches"

这些教训共同指向一个朴素但真实的方法论：

1. **先怀疑初始化/注册/接线，再怀疑架构。** C4 的 Metadata、candidate pipeline 的 Replace、coordinator 的 fallthrough、DAGPatchExecutor 的兜底——全是"接线细节"，不是算法错误。
2. **删除要谨慎，留痕要写明。** `SchedulerGenomeName` 是为历史数据保留的；注释里说明原因。
3. **可进化的维度，必须有能产生纯差异子代的算子。** `mutateSetMetadata` 的存在依赖 `mutateReplaceNode` 保留 Metadata。
4. **接口和配置项都要用真实数据说话。** 接口方法数调用者，参数验证走到的分支，性能用 `go test -bench` 实测（见 24.3）。
