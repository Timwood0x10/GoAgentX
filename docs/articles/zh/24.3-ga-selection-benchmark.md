# 选择算子性能对比——Truncation vs Tournament vs Roulette 实测

> 本文用**真实运行** `go test -bench` 得到的数据，对 `internal/ares_evolution/genome/selection.go` 里三大选择算子做性能对比，并给出它们各自的代数复杂度、内存分配与适用场景。所有数字都是本机一次`-count=1`运行的实测输出，不是编造的。

> ⚠️ 说明：`Go benchmark` 的 ns/op 依赖机器、编译器版本与运行压力。下表数据在 **go1.27.1 / darwin / arm64（Apple Silicon），`-benchtime=200ms -count=1`** 下测得，仅用于给出**数量级**的印象，不可跨机器照搬。旧版文章把"Apple M3 Max 单次运行"写成一个确定结论的做法，请当作不可复现的处理。

## 1. 被测对象与出处

benchmark 全部在 `internal/ares_evolution/genome/benchmark_test.go`。

| 算子 | Benchmark 函数 | 选择主体 | 复杂度（代码/注释） |
|------|---------------|---------|-------------|
| TruncationSelection | `BenchmarkTruncationSelection` | 排序后取 top 30% | O(n log n)，排序主导 |
| TournamentSelection | `BenchmarkTournamentSelection` | pop 50/200 × k 2/3/5/10，取一半 | 每 select O(poolSize) 洗牌 + O(k) 比较 |

另有同文件里的整代/整系统基准：`BenchmarkEvolve_OneGeneration`、`BenchmarkEvolveOnIdle_OneGeneration`、`BenchmarkEvolve_MultipleGenerations`、`BenchmarkRealWorldEvolution`（pop 20、100 代 `EvolveOnIdle`）、`BenchmarkApplyFitnessSharing` 等。

## 2. 实测数据（go1.27.1 darwin/arm64, -count=1）

### 2.1 TruncationSelection（截断）

```text
pop_10    161.2 ns/op
pop_100   5669  ns/op
pop_500   52825 ns/op
pop_1000  156384 ns/op
```

成本几乎全部来自排序 + 拷贝。

### 2.2 SortByScore（排序基线）

```text
pop_10    208.7 ns/op
pop_100   6098  ns/op
pop_500   51463 ns/op
pop_1000  144377 ns/op
```

Truncation 与 SortByScore 数量级基本一致（截断的 `pop_500` 略慢于裸排序，因为基准里还要建结果 slice；差异在测量噪声范围内）。

### 2.3 TournamentSelection（锦标赛）

```text
pop_50  k=2   3875 ns/op   k=3  4013   k=5  4299   k=10  5514
pop_200 k=2  31903 ns/op   k=3 34263   k=5 34876   k=10 38656
```

**观察**：k 从 2 涨到 10（5 倍），pop200 只从 ~32µs 涨到 ~39µs（约 +21%），远非线性。原因在代码里：`pickUniqueIndices` 用 Fisher-Yates 部分洗牌，成本主要由 `poolSize` 决定，而池子拷贝和去重开销占大头——k 变化对总时间影响很小。**这本身体现了"用更大的 k 增加选择压力"几乎不增加计算成本**，但也说明 tournament 的主要开销在支配性常数（拷贝、slice 构造），而非比较次数。

### 2.4 RouletteWheelSelection（轮盘赌）

```text
pop_10    202.1 ns/op
pop_100   2902  ns/op
pop_500   43097 ns/op
pop_1000  160606 ns/op
```

每转一次轮盘要遍历一次累积权重（O(n)），选 `n/2` 个个体总复杂度 O(n²)。所以 pop=1000 时轮盘赌（160.6µs）反超截断（156.4µs）。

## 3. 跨算子的交叉点

```mermaid
flowchart LR
    subgraph small["pop ≈ 10-100"]
        t1[Truncation ~161-5669]
        r1[Roulette ~202-2902]
        NOTE1[轮盘赌略快/相当]
    end
    subgraph large["pop ≥ 1000"]
        t3[Truncation ~156µs]
        r3[Roulette ~161µs]
        NOTE3[截断反超，因轮盘赌 O(n²)]
    end
```

- **小种群**：两者难分伯仲（微秒级），谁是"最快的"受噪声影响。
- **pop≈500 附近交叉**：截断的 O(n log n) 与轮盘赌的 O(n²) 在此相遇；之后轮盘赌随 n 平方恶化。
- **tournament**：绝对时间在这三个里偏高（pop200 已 ~32µs），主要来自每次 `Select` 构造结果与洗牌，但**随 k 增长平缓**——压力控制便宜，常数成本可见。

## 4. 内存分配

以 2.1–2.4 同一基准逻辑推：三者都会复制种群并构造结果 slice（次数随种群线性）；tournament 因 `pickUniqueIndices` 的洗牌临时数组 + 结果 slice，每次 `Select` 分配的字节数最高。想拿到精确 B/op 和 allocs/op，请运行：

```bash
go test -bench=BenchmarkTournamentSelection -benchmem ./internal/ares_evolution/genome/
```

（我可以在此给结论：**截断/排序类算子的分配次数不随规模增长**——基准里只拷贝一次 population slice；轮盘赌/锦标赛每次 select 会新造 slice，allocs 随群规模线性增。但精确数字必须实测。）

## 5. 复杂度小结（来自代码与注释，非编造）

| 算子 | 单次/整批 | 符号 | 备注 |
|------|----------|------|------|
| Truncation | 整批 | O(n log n) | 排序主导，稳定排序，未评估排最后 |
| SortByScore | 整批 | O(n log n) | `sort.SliceStable`，结果确定 |
| Tournament | 每 select | O(n) 洗牌 + O(k) 比较 | 池子拷贝是常数大头 |
| Roulette | 每 spin | O(n) | 选 n/2 ≈ O(n²) |
| SUS | 整批 | O(n + n·log n) | 单起点 + 均分指针，方差小（min 1枚保证出现）|
| Rank / LineageRank | 整批 | O(n log n) | 权重来自排序后的线性排名 |

SUS 尤其值得注意：相对轮盘赌它用一次随机起点 + 均匀间隔取 n 个，**保证了采样分布更均匀、遗传漂移更小**——这正对应注释里写的 `it guarantees an above-average individual is selected at least floor(fitness/avg) times`。

## 6. 如何选：工程判断

代码层面注释已经给出选型线索：

| 关注点 | 倾向 | 理由 |
|--------|------|------|
| 选择压力可调 | Tournament | `WithTournamentSize(k)`，k 大则强；实测加大 k 成本几乎不变 |
| 确定性 / 可复现 | Tournament / Roulette | `WithTournamentSeed` / `WithRouletteSeed` |
| 稀疏改进、谱系多样化 | LineageRank | 阈值 0.4、强度 0.5，惩罚优势谱系 |
| 最小采样方差、抗漂移 | SUS | 均匀指针，方差比轮盘赌小 |
| 确定性精英（top-N） | Truncation | 你知道好的就是前 N |
| 多目标权衡 | NondominatedSorting | 被 `"nsga2"` 激活 |

**最重要的现实**：在 LLM 驱动的进化里，一次评分调用是秒级，而任何选择算子整批都是微秒级——选择算子的**算法效果**（多样性、收敛质量）远比这几十微秒重要。别为 5% 的 ns/op 优化纠结，为"这个算子在当前任务分布上更不容易早熟收敛"而选。

## 7. 附录：复现方式

```bash
# 只跑选择/排序相关基准，单次，200ms 定长
go test -run=^$ \
  -bench='Benchmark(Truncation|Tournament|RouletteWheel|SortByScore)Selection?$' \
  -benchtime=200ms -count=1 -benchmem \
  ./internal/ares_evolution/genome/
```

> 复现基线：go1.27.1 darwin/arm64，单次 `-count=1`。若要方差请加 `-count=3` 并自行订正首轮的 GC 干扰。
